## 1. Executive Summary & Evolution of Benchmark Harnesses

The repository contains two distinct generations of benchmark tooling across its git history:

1. **Generation 1 (Legacy In-Memory Simulation - Commits `48b365f` to `3868a5a`):**
   - The legacy `perf/run-benchmark.py` and `benchmarks/runner.sh` did **not** execute load against a running service.
   - They modeled transaction concurrency as in-memory Python delays (`random.expovariate` and arbitrary queue multipliers).
   - This generated the 240 synthetic JSON result files and artificial headline throughput numbers (3,906 TPS, 3,420 TPS, 2,890 TPS, 1,020 TPS).
   - **Resolution:** Purged entirely in commit `3868a5a` (WP-GATE-2). Zero legacy files remain.

2. **Generation 2 (Live OpenJDK 21 + PostgreSQL 16 + k6 - Commit `386a81d`):**
   - In commit `386a81d`, `perf/run-benchmark.py` was rewritten to spawn real OpenJDK 21 Spring Boot JVM processes (`services/ledger-service-1.0.0-SNAPSHOT.jar`, PIDs 362743–364432) against PostgreSQL 16.
   - It executed real `perf/bin/k6` driving `perf/workloads/w2-mixed.js` over HTTP, committing ~116,395 double-entry journals into PostgreSQL.
   - **Limitation:** While executing against real binaries, it ran abbreviated 30-second measurement windows without warm-up discard and omitted per-cell database snapshot restores.
   - **Resolution:** Documented in [benchmark-inventory.md](file:///mnt/nexus/paycore/docs/audit/benchmark-inventory.md). Final sign-off benchmarks will execute the full Tier 1 matrix (72 runs, 10,000 sellers, 30s warm-up + 120s measured) per Playbook Section 9.

## 2. Inventory of Strategies in Production Code

The four benchmarked strategies exist as fully implemented, distinct Spring components in `services/ledger-service`:

| Strategy | Spring Component Class | Selection Mechanism | Concurrency Behavior |
|:---|:---|:---|:---|
| **S0_PESSIMISTIC** | `S0PessimisticStrategy.java` | `@ConditionalOnProperty(name="paycore.ledger.strategy", havingValue="S0_PESSIMISTIC")` | Acquires row-level pessimistic write lock (`SELECT ... FOR UPDATE`) on accounts in lexicographical ID order at transaction inception. |
| **S1_LATE_LOCK** | `S1LateLockStrategy.java` | `@ConditionalOnProperty(name="paycore.ledger.strategy", havingValue="S1_LATE_LOCK")` | Executes validation without locks; acquires pessimistic locks immediately before writing ledger entries. |
| **S2_STRIPED** | `S2StripedStrategy.java` | `@ConditionalOnProperty(name="paycore.ledger.strategy", havingValue="S2_STRIPED")` | Partitions hot platform accounts across 16 independent stripe rows (`account_stripes`), using randomized stripe hashing. |
| **S4_LEDGER_ONLY** | `S4LedgerOnlyStrategy.java` | `@ConditionalOnProperty(name="paycore.ledger.strategy", havingValue="S4_LEDGER_ONLY")` | Bypasses cached account row updates entirely for hot accounts; appends immutable ledger entries and reconstructs balances from snapshots + delta query. |
