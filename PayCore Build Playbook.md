## 1. Project summary

**PayCore** is a payments back office for a marketplace platform, built in Java. It records every movement of money in a double-entry ledger, settles money with a (simulated) payment provider, reconciles the provider's settlement files and bank deposits against the ledger, and turns every mismatch into a tracked case with a deadline.

**The problem it solves.** A marketplace charges buyers, keeps a platform fee, and pays sellers later. Three things go wrong in real systems: (1) balances become a bottleneck because every payment touches the same few accounts (the platform fee account); (2) the provider's bank deposit covers many orders at once, minus fees and refunds, so finance cannot match it by hand; (3) mismatches live in spreadsheets with no owner or deadline.

**Personas**

| Persona | Role claim | What they do |
| --- | --- | --- |
| Merchant (seller) | `MERCHANT` | Sees own balance, held funds, payouts and statement |
| Ops Analyst | `ANALYST` | Runs reconciliation, works cases, proposes adjustments |
| Admin | `ADMIN` | Approves large adjustments, manages users, runs batches |
| Service | `SERVICE` | Machine identity for service-to-service calls |

**Goals**

- G1: Correct money movement: idempotent, balanced, auditable, safe under concurrency and crashes.
- G2: Hot-account handling: compare several strategies with a reproducible benchmark and keep the best.
- G3: Settlement: batch payable funds, create payouts, ingest provider files.
- G4: Reconciliation: fee-aware many-to-one matching with explainable results.
- G5: Exception management: cases, SLAs, escalation, maker-checker adjustments.
- G6: Production habits: JWT security, observability, CI, tests, documentation.

**Non-goals (do not build)**

- Real payment rails, card data, PCI scope, KYC/AML engines.
- Multi-currency or FX (the schema carries a currency column; v1 uses INR only).
- Kubernetes, service mesh, multi-region, schema registry.
- AI/LLM features. This project is deliberately core engineering.

**Success criteria (all must be demonstrable)**

- S1: Property and concurrency tests prove debits equal credits after any sequence of operations.
- S2: A crash test (kill the service mid-load, restart, re-check invariants) passes repeatedly.
- S3: A benchmark report compares at least three hot-account strategies on the same workload and hardware.
- S4: Reconciliation matches seeded synthetic data and reports its match rate per rule.
- S5: `docker compose up` brings the whole system up with seed data; the console works end to end.
- S6: CI is green: format check, unit tests, integration tests, coverage gate.

## 3. Domain and accounting model

### 3.1 Money rules

- Amounts are `long` minor units (paise) in Java and `BIGINT` in PostgreSQL. Never use `float` or `double`. Provide a small `Money` value object (amount, currency) in the shared library.
- v1 currency is `INR`; validate the currency code on every request.
- All timestamps are UTC (`timestamptz`). Services take an injectable `java.time.Clock`.
- Fee calculation: `fee = round_half_up(gross * feeBps / 10000)`, `sellerShare = gross - fee`. The seller receives the remainder so the journal always balances exactly.

### 3.2 Chart of accounts

System accounts (exactly one each) and per-seller accounts. `normal side` decides how balance is read: balance = (sum of entries on the normal side) minus (sum on the other side).

| Account | Type | Normal side | Meaning |
| --- | --- | --- | --- |
| PROVIDER\_RECEIVABLE | ASSET | DEBIT | Money the provider owes the platform for captured payments |
| BANK\_CASH | ASSET | DEBIT | Platform bank balance |
| PAYOUT\_IN\_TRANSIT | LIABILITY | CREDIT | Payouts sent but not yet confirmed |
| PLATFORM\_FEE\_REVENUE | REVENUE | CREDIT | Platform fee earned (a hot account) |
| PROVIDER\_FEE\_EXPENSE | EXPENSE | DEBIT | Fees the provider charges the platform |
| WRITE\_OFF\_EXPENSE | EXPENSE | DEBIT | Unrecoverable differences written off |
| SELLER\_PAYABLE (per seller) | LIABILITY | CREDIT | Owed to the seller and available for payout |
| SELLER\_HELD (per seller) | LIABILITY | CREDIT | Owed to the seller but on hold |

### 3.3 Journal templates

Every operation posts one balanced journal (amounts in paise; G = gross, F = fee, S = seller share).

| Operation | Debit | Credit |
| --- | --- | --- |
| Capture payment | PROVIDER\_RECEIVABLE G | SELLER\_PAYABLE S; PLATFORM\_FEE\_REVENUE F |
| Place hold H | SELLER\_PAYABLE H | SELLER\_HELD H |
| Release hold H | SELLER\_HELD H | SELLER\_PAYABLE H |
| Refund R (proportional split into S\_r and F\_r) | SELLER\_PAYABLE S\_r; PLATFORM\_FEE\_REVENUE F\_r | PROVIDER\_RECEIVABLE R |
| Payout requested P | SELLER\_PAYABLE P | PAYOUT\_IN\_TRANSIT P |
| Payout confirmed P | PAYOUT\_IN\_TRANSIT P | BANK\_CASH P |
| Payout failed P | PAYOUT\_IN\_TRANSIT P | SELLER\_PAYABLE P |
| Provider deposit (net D, fees E) | BANK\_CASH D; PROVIDER\_FEE\_EXPENSE E | PROVIDER\_RECEIVABLE (D+E) |
| Fee variance adjustment X | PROVIDER\_FEE\_EXPENSE X | PROVIDER\_RECEIVABLE X |
| Write-off X | WRITE\_OFF\_EXPENSE X | PROVIDER\_RECEIVABLE X |

Capture with an automatic hold: when the seller's hold policy applies, the seller share is split inside the same journal between SELLER\_PAYABLE (S minus H) and SELLER\_HELD (H), where H = round\_half\_up(S \* holdBps / 10000). Refund rule: the seller portion is `S_r = round_half_up(R * S / G)` and the fee portion is the remainder `F_r = R - S_r`, so refunds balance exactly. The refund fee policy is configurable (`PROPORTIONAL` default). SELLER\_PAYABLE may go negative only through refund or dispute journals (the seller then owes the platform). Payout requests may never overdraw it.

### 3.4 Invariants (each must have an automated test)

- I1: Every journal has at least two lines, positive amounts, and total debits equal total credits.
- I2: Ledger entries are immutable. A database trigger rejects UPDATE and DELETE.
- I3: Globally, total debits equal total credits.
- I4: Each cached account balance equals the sum of its entries (striped accounts: sum of stripes).
- I5: Payout requests never exceed available SELLER\_PAYABLE.
- I6: A request with a given idempotency key produces at most one journal.
- I7: Total refunds for a payment never exceed captured amount.
- I8: Each journal links to exactly one business operation (payment, refund, hold, payout, adjustment), enforced by a unique constraint.

## 4. Architecture

```
 Browser --> nginx (web/ops-console, port 8080)
              |  /api/identity/*  --> identity-service   :8081
              |  /api/ledger/*    --> ledger-service     :8082
              |  /api/settlement/* --> settlement-service :8083

 identity-service --- PostgreSQL db: identity      Redis (token deny-list)
 ledger-service   --- PostgreSQL db: ledger        Redis (rate limit, cached balances)
 settlement-service - PostgreSQL db: settlement    (provider simulator runs inside, profile `sim`)

 ledger-service ==Kafka topic ledger.domain-events==> settlement-service
 settlement-service ==Kafka topic settlement.events==> (console metrics, audit)
 settlement-service --REST (service token)--> ledger-service (payouts, deposits, adjustments)
```

| Service | Port | Database | Responsibility |
| --- | --- | --- | --- |
| identity-service | 8081 | `identity` | Users, roles, login, refresh, logout, JWKS, service tokens |
| ledger-service | 8082 | `ledger` | Accounts, journals, capture, refund, holds, statements, integrity checks |
| settlement-service | 8083 | `settlement` | Candidates, batches, payouts, provider files, reconciliation, cases, adjustments |
| ops-console | 8080 | none | React single-page app served by nginx |

Principles:

- **Data ownership.** Each service owns its database. No service reads another's tables.
- **Commands are synchronous, facts are events.** REST for commands that must succeed or fail now; Kafka events for things that happened.
- **At-least-once events with idempotent consumers.** Producers use the transactional outbox. Consumers dedupe on `eventId` using a `processed_events` table.
- **Failure isolation.** If settlement-service is down, the ledger keeps working and events wait in Kafka. If Kafka is down, the ledger keeps working and events wait in the outbox table.
- **Single PostgreSQL instance, three databases** in Compose to save memory (created by an init script).

## 7. Identity service

Purpose: the only place that knows passwords and issues tokens. Everything else only verifies tokens. Adapt IssueFlow's auth classes (Section 6.2) but change the design as follows.

### 7.1 Features

| ID | Feature | Rules |
| --- | --- | --- |
| F-I-01 | Login `POST /auth/login` | Username and password. BCrypt (cost 12). Returns access token in the JSON body and sets the refresh token as an httpOnly, Secure, SameSite=Strict cookie scoped to `/api/identity/auth`. Generic failure message for unknown user or wrong password |
| F-I-02 | Refresh `POST /auth/refresh` | Reads the cookie. Rotates: the old refresh token is marked used and a new one is issued in the same token family. Reuse of an already-used token revokes the whole family and writes an audit record |
| F-I-03 | Logout `POST /auth/logout` | Revokes the refresh family, clears the cookie, and writes the access token's `jti` to the Redis deny-list with a TTL equal to its remaining life |
| F-I-04 | Current user `GET /auth/me` | Returns id, username, roles, and `sellerId` for merchants |
| F-I-05 | JWKS `GET /.well-known/jwks.json` | Public keys with `kid`. Supports two keys at once (current and previous) so keys can rotate without downtime |
| F-I-06 | Service token `POST /auth/service-token` | `client_id` and `client_secret` (BCrypt-hashed in `service_clients`). Returns a JWT with role `SERVICE`, lifetime 10 minutes. Callers cache it until 60 seconds before expiry |
| F-I-07 | User admin (ADMIN only) | Create, list, change roles, disable. An admin cannot disable or demote themselves |
| F-I-08 | Login protection | Redis token bucket per IP and per username. Five consecutive failures lock the username for 15 minutes. Locked and unknown users return the same response shape |
| F-I-09 | Audit | Login success and failure, logout, refresh reuse, role change, user disable. Append-only table |

### 7.2 Token design

- Algorithm RS256. Access token lifetime 15 minutes. Claims: `sub` (user id), `iss` (`paycore-identity`), `aud` (`paycore`), `roles` (array), `sellerId` (merchants only), `jti`, `iat`, `exp`.
- Refresh token: 256 bits of random data, stored only as a SHA-256 hash, 7-day life, fields `family_id`, `used_at`, `revoked_at`.
- The console keeps the access token in memory only. It never writes tokens to `localStorage` (IssueFlow does; fix this in the pull).
- Resource servers (ledger, settlement) validate signature via `jwk-set-uri`, check `iss` and `aud`, map `roles` to `ROLE_*`, and check the Redis deny-list through a custom token validator. If Redis is unavailable the deny-list check is skipped, a metric is incremented and a warning logged: access tokens are short-lived, so this trade-off is accepted. Record it as an ADR.
- Private keys come from environment variables or a mounted volume. Only the `dev` profile may generate a key at startup.

## 8. Ledger service

### 8.1 The posting engine (core of the system)

Every money movement goes through one internal method, `PostingEngine.post(JournalRequest)`. Controllers never write ledger rows directly.

Steps inside one database transaction:

1. Validate: at least two lines, positive amounts, debits equal credits (I1), known accounts, matching currency.
2. Idempotency: claim the idempotency record (Section 8.2). If the key is already completed with the same request hash, return the stored response without posting.
3. Business-rule checks for the operation (limits, available balance, refund ceiling).
4. Lock accounts according to the active strategy (Section 9). Locking order is deterministic everywhere, which prevents deadlocks.
5. Insert the journal header and all entries.
6. Apply balance changes as the strategy dictates.
7. Insert the outbox event rows and the audit row.
8. Store the idempotent response and commit.

Implementation notes: use `JdbcClient` with explicit SQL for steps 4 to 7. Keep the transaction short. Never call Kafka, Redis or HTTP inside the transaction. Entries carry `journal_id`, `account_id`, `side`, `amount`, `created_at`.

### 8.2 Idempotency framework (F-L-10)

- Required header `Idempotency-Key` (8 to 64 visible ASCII characters) on every write endpoint.
- Table `idempotency_keys(scope, key, request_hash, status, response_status, response_body, created_at, completed_at)` with a unique constraint on `(scope, key)`. Scope is the client or user id from the token.
- Same scope, key and request hash after completion: replay the stored response with an `Idempotent-Replayed: true` header, no new journal, no new event.
- Same key, different request hash: `422 idempotency_key_reused`.
- Same key while the first request is still running: `409 request_in_progress`.
- A scheduled job deletes completed records older than 7 days.

### 8.3 Features

| ID | Feature | Endpoint | Key rules |
| --- | --- | --- | --- |
| F-L-01 | Seller onboarding | `POST /v1/sellers` | Creates the seller's SELLER\_PAYABLE and SELLER\_HELD accounts. Body: `sellerId`, `displayName`, `holdBps` (0 to 10000), `holdDays` (0 to 30). Idempotent by `sellerId`. Roles: ADMIN, SERVICE |
| F-L-02 | Capture payment | `POST /v1/payments` | Body: `orderId`, `sellerId`, `providerTxnId`, `grossAmount`, `currency`, optional `feeBps` (default 1000, allowed 0 to 3000), `capturedAt`. Computes fee and seller share (Section 3.1). One balanced journal: debit PROVIDER\_RECEIVABLE gross; credit SELLER\_PAYABLE (seller share minus held part); credit SELLER\_HELD (held part); credit PLATFORM\_FEE\_REVENUE fee. A `holds` row with `release_at = capturedAt + holdDays` is created in the same transaction when the held part is above zero. Unique `providerTxnId` and `orderId`: a repeat with a different key returns `409 duplicate_payment`. Response 201: `paymentId`, `journalId`, `feeAmount`, `sellerAmount`, `heldAmount`, `status` |
| F-L-03 | Refund | `POST /v1/payments/{paymentId}/refunds` | Body: `amount`, `reason`. Also required: providerRefundTxnId (the provider's refund transaction id; unique, and the join key used in reconciliation). Refund must not exceed captured minus refunded (I7). Split per Section 3.3. SELLER\_PAYABLE may go negative. Payment status moves CAPTURED, PARTIALLY\_REFUNDED, REFUNDED |
| F-L-04 | Holds | `POST /v1/holds`, `POST /v1/holds/{id}/release` | Manual hold or release by ANALYST or ADMIN with a reason code (`NEW_SELLER`, `DISPUTE_RISK`, `MANUAL_REVIEW`). A scheduled job releases due holds automatically. Release is idempotent. Every hold has `reason`, `release_at`, `status` (ACTIVE, RELEASED) |
| F-L-05 | Payouts (service only) | `POST /v1/payouts`, `/{id}/confirm`, `/{id}/fail` | Request: lock the seller's payable row, require available at least the amount (I5), post debit SELLER\_PAYABLE credit PAYOUT\_IN\_TRANSIT. Confirm posts to BANK\_CASH. Fail reverses the request journal. State guard on the `payouts` table: REQUESTED to CONFIRMED or FAILED only |
| F-L-06 | Provider deposit (service only) | `POST /v1/provider-deposits` | Body: `depositId`, `netAmount`, `feeAmount`, `reference`, `valueDate`. Posts per Section 3.3. Settlement calls this when a bank deposit is matched to a provider file |
| F-L-07 | Adjustments (service only) | `POST /v1/adjustments` | Body: `adjustmentId`, debit account, credit account, amount, `caseId`, reason. Only system accounts allowed (PROVIDER\_RECEIVABLE, PROVIDER\_FEE\_EXPENSE, WRITE\_OFF\_EXPENSE, BANK\_CASH). Seller accounts are rejected in v1 |
| F-L-08 | Balances and statements | `GET /v1/sellers/{id}/balance`, `GET /v1/accounts/{id}/entries`, `GET /v1/journals/{id}` | Balance returns available (payable), held, and in-transit. Entries use keyset pagination on `(created_at, id)` with `limit` (default 50, max 200) and an opaque `cursor`. A MERCHANT may read only their own `sellerId` |
| F-L-09 | Integrity checker | `GET /v1/integrity` plus a nightly job | Verifies I3 and I4 and samples I1. Returns a report (checked counts, violations). Increments metric `ledger_integrity_violations_total`. Heavy checks run in batches by account id range |
| F-L-11 | Outbox and events | internal | Section 15.3 lists event types. Events are written inside the posting transaction and relayed afterwards |
| F-L-12 | Rate limiting | filter | Redis token bucket on all write endpoints keyed by token subject. Over limit returns 429. Redis down returns 503 (fail-closed) by default |
| F-L-13 | Audit | internal | Append-only record for every write with actor, request id, entity, before and after summary |

### 8.4 Error model

All services return RFC 9457 Problem Details (`application/problem+json`) with fields `type`, `title`, `status`, `detail`, `code`, `requestId`, `timestamp`. Codes are stable strings (for example `insufficient_available_balance`, `refund_exceeds_captured`, `duplicate_payment`, `idempotency_key_reused`, `request_in_progress`, `rate_limit_exceeded`). Validation errors list the failing fields.

## 9. Hot-account strategies and benchmark

### 9.1 The problem to demonstrate

PLATFORM\_FEE\_REVENUE and PROVIDER\_RECEIVABLE appear in every capture. If each transaction locks and updates those rows, transactions queue on those row locks and throughput stops scaling with concurrency. A public write-up of naive double-entry on a relational database reports this kind of ceiling; treat that as motivation, not as a number to claim for your own system.

Accounts carry a boolean `hot`. Only hot accounts use the selected strategy. All other accounts always use pessimistic locking. Strategy is chosen by `ledger.posting.strategy` (restart required; no mid-flight switching).

### 9.2 Strategies

Global lock order for every strategy: non-hot accounts first in ascending id, then hot accounts in ascending id. One global order means no deadlocks.

| ID | Name | Mechanism | Trade-off |
| --- | --- | --- | --- |
| S0 | PESSIMISTIC (baseline) | `SELECT ... FOR UPDATE` on all accounts in id order at transaction start, update balances | Simple and correct, hot rows serialize everything |
| S1 | LATE\_LOCK | Lock non-hot accounts first. Apply hot-account balance changes as the final statement, a single `UPDATE ... SET balance = balance + :delta` with no prior read, so the hot lock is held only briefly before commit | Cheap to implement. Gains are bounded because the hot row is still serialized |
| S2 | STRIPED | A hot account has N stripes in `account_stripes(account_id, stripe, balance)`. The stripe is `hash(journalId) mod N` (default N = 16). Reads sum all stripes | Writes spread over N rows. Reads cost more and need the sum to be consistent for reports |
| S3 | BATCHED (optional stretch) | The ledger entry is inserted inside the request transaction, but hot balance deltas go to a bounded in-memory queue and a single writer applies them in aggregated updates every 50 ms or 200 deltas | Fewer hot-row updates. Balance cache lags; after a crash it must be recomputed from entries on startup. Highest complexity |
| S4 | LEDGER\_ONLY | Hot accounts have no live balance row. Writes only insert entries. Balance is the latest snapshot plus the sum of entries after the snapshot entry id. A scheduled job writes snapshots | Best write path (append only). Reads need snapshot plus delta, so cache them briefly for dashboards |

Mandatory: S0, S1, S2, S4. S3 only if time remains after everything else. Payout and refund decisions use SELLER\_PAYABLE, which is not hot, so they are never based on cached or lagging balances. A Redis cache with a 5-second TTL may serve dashboard reads only.

Each strategy implements one interface (`BalanceStrategy`) with methods to lock, apply deltas and read balance. Add tests proving every strategy satisfies I1 to I8.

### 9.3 Benchmark protocol

| Item | Specification |
| --- | --- |
| Tool | k6 scripts in `perf/` driving the real REST API with valid JWTs and idempotency keys |
| Dataset | 10,000 pre-created sellers; fresh database per run from a snapshot |
| Workloads | W1: captures only. W2: mix of 70% captures, 20% refunds, 10% payout requests. W3: skewed, 80% of captures to 20% of sellers |
| Concurrency | 1, 8, 32, 64, 128 virtual users |
| Duration | 30 s warm-up (discarded) plus 120 s measured |
| Repeats | 3 runs per cell, report the median |
| Durability | Keep `synchronous_commit` at the default. If tested otherwise, report separately and label it clearly |
| Recorded environment | CPU model, cores, RAM, OS, Docker limits, Postgres settings, Java version, strategy parameters |
| Metrics | Successful requests per second, p50, p95 and p99 latency, error rate by type, database deadlocks (`pg_stat_database.deadlocks`), lock-wait samples, database container CPU |
| Validity rule | After every run, run the integrity checker. Any violation invalidates the run |
| Output | JSON per run in `perf/results/`, a script that builds the table in `docs/benchmark-report.md` |

Decision rule: the default strategy is the one with the highest sustained throughput at p99 under 250 ms (configurable) with zero invariant violations across all runs. Record the choice in an ADR with the table.

Honesty rules for the report: state that results come from one machine running containers; do not extrapolate; list limitations (synthetic data, single node); never copy numbers from other projects.

### 9.4 Crash and recovery test

Automate in `scripts/crash-test` and a Testcontainers test:

1. Start the system and run a mixed load (W2).
2. At a random moment between 5 and 30 seconds, kill the ledger container with `SIGKILL`.
3. Restart it. The load client replays every in-flight request with its original idempotency key.
4. Run the integrity checker. Assert: debits equal credits, every idempotency key has at most one journal, no payment has two journals, and the outbox contains each committed event exactly once.
5. Repeat at least 50 iterations. Write the result table to `docs/crash-test-report.md`.
6. Optional variant: kill the Postgres container instead, restart, and repeat the checks.

PostgreSQL already guarantees atomic commits. The value of this test is proving the application layer: idempotent retries, the outbox, and recovery of strategy state (S3 queue, S4 snapshots).

## 10. Settlement service

Two money flows exist and must not be confused:

- **Money in:** the provider collects from buyers and later pays the platform's bank account. Evidence: provider settlement files and bank deposits. Reconciled in Section 10.4.
- **Money out:** the platform pays sellers from the ledger balance. Evidence: payouts and bank payout confirmations. Handled in Section 10.2.

### 10.1 Expected-items read model

The service consumes `ledger.domain-events` and builds `settlement_candidates`, the expected side of reconciliation.

- Rows: `seller_id`, `payment_id`, `provider_txn_id`, `order_id`, `kind` (CAPTURE or REFUND), `gross`, `fee`, `seller_amount`, `held_amount`, `occurred_at`, `status` (NEW, BATCHED, RECONCILED).
- Consumer rules: dedupe through `processed_events(event_id primary key)` inserted in the same transaction as the candidate. Events are keyed by `paymentId`, so a refund always arrives after its capture on the same partition. On a processing error retry three times with backoff, then publish to `ledger.domain-events.dlq` and raise a metric.
- Never read the ledger database. When the service needs a balance it calls the ledger API with a service token.

### 10.2 Batches and payouts

| ID | Feature | Rules |
| --- | --- | --- |
| F-S-01 | Run batch `POST /v1/batches/run` (ADMIN, SERVICE) plus a daily cron | Takes a cutoff time `T`. Uses a PostgreSQL advisory lock so only one run executes at a time. Links all NEW candidates with `occurred_at <= T` to the batch for traceability. For each seller with items or a positive balance, reads the available payable balance from the ledger. If it is at least `minPayoutAmount` (default 10000 paise), creates a payout with the deterministic id `batchId:sellerId`, capped at `maxPayoutAmount` per seller per batch (configurable) |
| F-S-02 | Request payout | Calls ledger `POST /v1/payouts` with idempotency key equal to the payout id. A failed or timed-out call is safe to retry because the id is deterministic. Re-running a batch resumes where it stopped |
| F-S-03 | Send payout file | Writes a simulated bank payout file (`payout_id, seller_id, amount, reference`) and marks payouts SENT |
| F-S-04 | Confirm or fail | The bank simulator returns a result file. Confirm calls ledger `/payouts/{id}/confirm`, failure calls `/fail` (funds return to payable). Both idempotent |
| F-S-05 | Payout views | List and filter payouts and batches with keyset pagination |

State machines: batch CREATED, PAYOUTS\_REQUESTED, SENT, COMPLETED or PARTIAL\_FAILURE. Payout REQUESTED, SENT, CONFIRMED or FAILED. Illegal transitions return `409 invalid_state_transition`.

Optional stretch: `payout.requires-reconciliation=true` restricts a seller's payout to the amount of their RECONCILED candidates, so sellers are paid only after the cash arrived. Default is false.

### 10.3 Provider simulator and file formats

The simulator runs only under the `sim` Spring profile and is disabled in `prod`. It turns the candidates into realistic files with injected faults, and writes a ground-truth manifest so match quality is measurable.

**Provider settlement file** (CSV, UTF-8, header row, trailer row):

| Column | Meaning |
| --- | --- |
| `provider_batch_id` | Batch the line belongs to |
| `provider_txn_id` | Provider transaction id (join key to `providerTxnId`) |
| `txn_type` | CAPTURE, REFUND, CHARGEBACK, FEE\_ADJUSTMENT |
| `merchant_ref` | The order id |
| `gross_amount`, `fee_amount`, `net_amount` | In paise. net = gross minus fee for captures |
| `currency`, `txn_time`, `settle_date` | INR, ISO timestamp, ISO date |

The trailer row carries line count and totals. The parser rejects a file whose trailer disagrees with its lines (`file_integrity_failed`).

**Bank statement file** (CSV): `bank_deposit_id, value_date, amount, currency, reference`. The reference text may name zero, one or several provider batch ids.

**Injected faults** (all rates configurable, deterministic through a random `seed`):

| Fault | Default rate |
| --- | --- |
| Line missing from provider file | 0.5% |
| Provider line with no ledger item | 0.2% |
| Duplicate provider line | 0.3% |
| Gross amount differs | 0.5% |
| Fee differs from the expected fee model | 1% |
| Two batches paid in one deposit | 10% of days |
| Reserve holdback (deposit lower by a fixed percent) | 5% of days |
| Line delayed to a later day | 1% |
| Reference text stripped | 20% of deposits |

**Ingestion rules:** files stream through a parser (never load a whole file in memory) and rows are inserted in JDBC batches of 1,000. The SHA-256 of each file is unique; uploading the same file again returns `409 file_already_ingested`. Line-level errors are recorded in `file_errors` (capped per file). Endpoints are in Section 12.

Expected provider fee model for variance checks: `expected_fee = round_half_up(gross * providerFeeBps / 10000) + providerFixedFee`, both configurable. A variance is flagged only when the absolute difference exceeds `feeToleranceMinor` (default 1 paisa).

### 10.4 Reconciliation engine

`POST /v1/recon/runs` with `fromDate` and `toDate` starts an asynchronous run (status RUNNING, COMPLETED, FAILED, with progress counters). Re-running the same range is safe: matches are recreated and cases are never duplicated (case uniqueness key below).

**Stage 1: line matching** (candidates against provider lines, joined on `provider_txn_id`, processed in chunks by `settle_date`, hash-join in memory per chunk).

| Outcome | Rule |
| --- | --- |
| MATCHED\_EXACT | Same type and gross |
| AMOUNT\_MISMATCH | Gross differs |
| FEE\_VARIANCE | Fee differs from the expected fee model beyond tolerance |
| DUPLICATE\_PROVIDER\_LINE | Same `provider_txn_id` twice |
| MISSING\_IN\_PROVIDER | Candidate older than the grace period (default 3 days) with no provider line |
| MISSING\_IN\_LEDGER | Provider line with no candidate |

**Stage 2: fuzzy fallback** for items still unmatched. First try `merchant_ref` equals the order id. Otherwise match on equal amount, a time window of plus or minus 10 minutes, and a unique candidate. Accept only if exactly one candidate qualifies and the score reaches the threshold; otherwise leave it for a case. Never guess between several candidates.

**Stage 3: batch to deposit.** For each provider batch the expected deposit is the sum of its net amounts (verified against the file trailer). Match against bank deposits with `value_date` in `[settle_date, settle_date + 3 days]`:

1. Exact: one deposit equals one batch's net amount.
2. Reference hint: parse provider batch ids found in the deposit reference.
3. Subset search: find a subset of still-unmatched batches whose net total equals the deposit amount (first with zero tolerance, then with the configured reserve-holdback tolerance). Use dynamic programming over reachable sums with a state cap, or meet-in-the-middle for up to 40 batches, and a 5-second time limit. If more than one subset fits, mark AMBIGUOUS and open a case. Subset sum is NP-hard in general, so the size limits and time limit are part of the design; document them.

**Stage 4: posting.** When a deposit is matched, call ledger `POST /v1/provider-deposits` with idempotency key `deposit:<depositId>`. A deposit with no match yields a `DEPOSIT_UNMATCHED` exception.

**Explainability and metrics.** Every match stores `rule`, `confidence` and an `evidence` JSON. Each run records: counts per rule, overall match rate, duration, and (when ground truth exists) precision and recall per fault type against the simulator's manifest. Only report rates that come from these stored results.

Tables involved: `recon_runs`, `recon_matches`, `recon_exceptions`, plus links to provider lines and deposits.

### 10.5 Cases, SLAs and escalation

Every exception becomes a case. Uniqueness key: `(exception_type, reference)` with a unique index, so repeated runs never create duplicates.

| Field | Rule |
| --- | --- |
| Types | The exception types from Section 10.4 |
| Severity | CRITICAL if amount is at least 5,000,000 paise; HIGH at least 1,000,000; MEDIUM at least 100,000; otherwise LOW. DEPOSIT\_UNMATCHED and DUPLICATE\_PROVIDER\_LINE are at least HIGH. Thresholds are configurable |
| SLA due | CRITICAL 4 hours, HIGH 24 hours, MEDIUM 72 hours, LOW 7 days (configurable) |
| States | OPEN, IN\_REVIEW, ESCALATED, RESOLVED, WRITTEN\_OFF |
| Transitions | OPEN to IN\_REVIEW; IN\_REVIEW to RESOLVED or WRITTEN\_OFF; any non-terminal to ESCALATED (automatic); ESCALATED to IN\_REVIEW. RESOLVED and WRITTEN\_OFF are terminal |
| Concurrency | `version` column (optimistic locking). A conflicting update returns `409 case_modified` |
| Assignment | Assign to a user or claim for yourself. Starting work requires an assignee |
| Comments | Append-only, with author and time |
| Escalation job | Every minute: non-terminal cases past `due_at` and not yet escalated move to ESCALATED, severity rises one level (maximum CRITICAL), `due_at` extends by half the SLA, an event `CASE_ESCALATED` is emitted and an audit row written |

Adapt IssueFlow's scheduled escalation and optimistic-locking code for this (Section 6.2); the state machine and rules above replace its ticket logic.

### 10.6 Adjustments with maker-checker

An analyst proposes an adjustment from a case. Only fixed templates are allowed:

| Template | Debit | Credit |
| --- | --- | --- |
| FEE\_VARIANCE | PROVIDER\_FEE\_EXPENSE | PROVIDER\_RECEIVABLE |
| WRITE\_OFF | WRITE\_OFF\_EXPENSE | PROVIDER\_RECEIVABLE |

States: PROPOSED, APPROVED, POSTED or REJECTED. The approver must be an ADMIN and must differ from the proposer. After approval, the service calls ledger `POST /v1/adjustments` with idempotency key `adjustment:<id>`. On success the adjustment becomes POSTED and the case becomes RESOLVED (or WRITTEN\_OFF for write-offs). If the call fails the adjustment stays APPROVED and a retry job posts it later. Every step is audited and emits an event.

## 14. Security, observability and operations

### 14.1 Security hardening checklist

- Validate all input with Bean Validation and reject unknown enum values. Request body size limits on every endpoint; file uploads capped (default 20 MB).
- Same-origin deployment behind nginx, so CORS stays disabled. Do not add wildcard CORS.
- Actuator exposes only `health`, `info` and `prometheus`, on a separate management port that nginx does not proxy.
- Never log tokens, passwords, secrets or full request bodies. Mask identifiers where sensible.
- Secrets come from environment variables or mounted files; `.env.example` lists names with placeholder values. The `prod` profile refuses to start with default or empty secrets.
- Dependency hygiene: Dependabot for Maven, npm and GitHub Actions; dependency review on pull requests.
- Least privilege: one database role per service; Kafka topics created explicitly, not auto-created.
- Local Compose uses plain HTTP. Any real deployment must sit behind TLS (see Section 16.3).

### 14.2 Observability

- Structured JSON logs (Spring Boot structured logging, available from 3.4) containing `requestId`, service name and level. The request id travels from the console through every service call and into Kafka headers.
- Micrometer metrics scraped by Prometheus. Required metrics:

| Metric | Type | Tags |
| --- | --- | --- |
| `ledger_posting_duration_seconds` | Timer | `operation`, `strategy` |
| `ledger_posting_failures_total` | Counter | `operation`, `code` |
| `ledger_integrity_violations_total` | Counter | `check` |
| `idempotency_replays_total` | Counter | `endpoint` |
| `outbox_pending_events` | Gauge | `service` |
| `outbox_publish_failures_total` | Counter | `service` |
| `denylist_check_skipped_total` | Counter | `service` |
| `recon_run_duration_seconds` | Timer | none |
| `recon_match_rate` | Gauge | last run |
| `cases_open` | Gauge | `severity` |
| `cases_sla_breached_total` | Counter | `severity` |
| `payout_requests_total` | Counter | `status` |

- Health: liveness is process only; readiness checks the database and Redis. Kafka is intentionally not part of readiness because the outbox lets money paths continue while Kafka is down.

### 14.3 Runbook (`docs/runbook.md`)

Write one short entry per scenario in the form symptom, check, fix: service will not start; outbox backlog growing; Kafka unavailable; Redis unavailable (rate limiter fail-closed behaviour and deny-list skip); integrity violation alert; consumer messages in the dead-letter topic (how to replay); stuck settlement batch (safe re-run); signing key rotation; restoring a database backup.

## 16. Code quality, CI/CD and deployment

### 16.1 Code conventions

**Package structure** is by module first, then layer inside the module. Example for ledger-service: `posting`, `payment`, `refund`, `hold`, `payout`, `account`, `statement`, `integrity`, `idempotency`, `outbox`, `ratelimit`, `audit`, `security`, `common`. Inside a module: `api` (controllers and request/response records), `domain` (rules, no framework imports where practical), `app` (use-case services and transactions), `infra` (SQL repositories, clients).

**Rules**

- Controllers are thin: validate, call one use case, map the result. Entities and database rows never appear in API responses; use record DTOs.
- Constructor injection only. No field injection. Prefer immutable types (records, `final` fields).
- Money is `long` paise via the `Money` type. Time comes from an injected `Clock`.
- Business rules live in the domain layer. SQL is used for persistence, locking and atomic updates, not hidden business logic.
- Domain exceptions carry a stable `code` and are mapped centrally to Problem Details. No stack traces in responses.
- Logging through SLF4J only, no `System.out`, no sensitive data.
- Methods stay short and cohesive (guideline: 40 lines). Comments explain why, not what. Public domain methods that encode a money rule get a Javadoc stating the rule and the invariant it protects.
- No dead code, no commented-out code, no unused dependencies, no TODO without an issue reference.

**Automated checks (all enforced in CI)**

- Spotless formatting check (google-java-format or palantir-java-format; pick one in an ADR).
- Maven Enforcer: Java 21, dependency convergence, no snapshots.
- SpotBugs on main code; fix findings or suppress with a written reason.
- ArchUnit: `api` does not call `infra` directly; `domain` does not depend on `api` or `infra`; no cycles between modules; no `System.out`; controllers do not use repositories.
- JaCoCo coverage gates (Section 15.2).
- Frontend: TypeScript strict (no `any`), ESLint with the React hooks rules, Prettier, typecheck, tests.

**Git and documentation**

- Short-lived branches, pull requests with a template (what, why, how tested), Conventional Commits, protected `main`.
- ADRs in `docs/adr/NNN-title.md` (context, decision, consequences). Required ADRs: formatter choice, Java and Boot versions, JWT design and deny-list trade-off, posting strategy choice, money representation, event delivery semantics, reconciliation limits.
- Every service README: purpose, how to run, configuration table, link to OpenAPI, and a "How it works" section.

### 16.2 Continuous integration (GitHub Actions)

| backend | Matrix over the three services and the common library: `./mvnw -B verify` (Spotless check, unit tests, Testcontainers integration tests, JaCoCo gate, SpotBugs). Cache Maven | Every push and pull request |

## 18. Known pitfalls checklist

- Never use floating point for money. Use `Math.addExact` and `Math.multiplyExact` in fee arithmetic.
- Compute fees and splits with one shared function. Test boundary cases: 1 paisa, odd amounts, 100% refund, partial refunds that sum to the total.
- One global lock order (non-hot ascending id, then hot ascending id) for every strategy and every operation, including payouts and adjustments.
- Under the default READ COMMITTED isolation, a read followed by a write is unsafe without a lock or an atomic `UPDATE`. Document the isolation level used by each critical operation.
- Do not call Kafka, Redis or HTTP inside a database transaction. The outbox exists for this reason.
- Idempotency: scope keys by caller, store the request hash, distinguish replay, mismatch and in-flight, and clean up old keys.
- Outbox relay must claim rows with `FOR UPDATE SKIP LOCKED`, publish outside the transaction, and mark published afterwards. Delivery is at least once.
- Consumers must dedupe before applying effects, inside the same transaction as the effect.
- Keyset pagination only. Do not use `OFFSET` for entries or lines.
- Flyway: never edit an applied migration; add a new one. Do not rely on Hibernate to create schema.
- Uploaded files: stream, limit size, verify the trailer, reject duplicates by hash, never trust column counts.
- Subset search needs hard limits (state cap, time limit). Never guess when more than one solution fits.
- Refresh tokens: rotate on every use and revoke the family on reuse. Never log token values.
- Time: store UTC, inject `Clock`, never call `Instant.now()` in domain code.
- Testcontainers tests need Docker; keep slow tests in the integration phase, not in unit runs.
- Benchmarks on a laptop with other applications open are noisy: close other workloads, run three times, record the environment.
- Never claim numbers that are not in a generated report.
