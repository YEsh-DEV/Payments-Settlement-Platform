## 2. WP-GATE-2A: Real Process Crash Testing

### 2.1 The Issue with Previous Implementation
The initial harness executed an in-process Python HTTP server backed by SQLite (`sqlite3` / `BaseHTTPRequestHandler`) launched via `sys.executable ... --service`. The reported 67.92 ms recovery time measured Python thread sleep, not real Spring Boot JVM startup and PostgreSQL WAL recovery.

### 2.2 Corrective Action
1. Built the real Spring Boot jar: `services/ledger-service/target/ledger-service-1.0.0-SNAPSHOT.jar` (OpenJDK 21, Spring Boot 3.3.6).
2. Rewrote `scripts/crash-test`:
   - Spawns real JVM via `subprocess.Popen(['java', '-jar', ...])` against native PostgreSQL 16.6 (port 5432) and Redis 8.10 (port 6379).
   - Captures PID, command line from `/proc/<pid>/cmdline`, jar SHA-256, and PostgreSQL version to `docs/audit/evidence/crash-test-process.txt`.
   - Sends concurrent Workload W2 traffic over HTTP.
   - Issues real host kernel `SIGKILL` (signal 9 / `kill -9 <pid>`).
   - Relaunches the JVM, polls `/actuator/health` to `UP`, measures real recovery time (~6.1 to 8.9 seconds).
   - Replays all in-flight and succeeded requests with original `Idempotency-Key` headers.
   - Audits Assertions A through F directly in PostgreSQL (`I3`, `I6`, `I8`, outbox completeness, zero ghost 201s, zero duplicate journals on replay).
3. Variant 2 (PostgreSQL SIGKILL):
   - Kills PostgreSQL master process via `SIGKILL`, restarts via `pg_ctl`, verifies WAL recovery, confirms zero data corruption or invariant violations.
4. Renamed `SigkillRecoveryVerificationTest.java` to `IdempotencyReplayAfterRestartTest.java` and clarified its role as a unit test for rollback and branch logic.

## 3. WP-GATE-2B: Benchmark Provenance & Cleanup

### 3.1 Provenance Finding
Auditing `perf/run-benchmark.py` revealed that the 240 benchmark JSON files were generated by a Python mathematical equation (`simulate_strategy_latency`) using `random.expovariate` and queue delay multipliers, without making any HTTP requests to Spring Boot or PostgreSQL.

### 3.2 Actions Taken
1. Authored `docs/audit/benchmark-provenance.md` and captured raw code evidence in `docs/audit/evidence/benchmark-provenance.txt`.
2. Deleted all 240 synthetic JSON result files from `perf/results/`.
3. Excised fabricated numbers (3,906 req/s, 3,420 TPS, 2,890 TPS, 1,020 TPS) from `README.md`, `docs/benchmark-report.md`, `docs/hot-account-report.md`, and `web/ops-console/src/pages/SystemPage.tsx`.
4. Consolidated `benchmarks/k6/` into `perf/k6/` and deleted the redundant `benchmarks/` directory.
5. Rebuilt ops-console cleanly (`npm run build` completed in 1.59s with 0 errors).
6. Removed `agent_report.md` from the repository.

### 3.3 Benchmark Rerun Proposal
Per the stopping rule, benchmark execution is paused pending the owner's decision between:
- **Option A (Full Matrix):** 4 strategies $\times$ 3 workloads $\times$ 5 concurrencies $\times$ 3 repeats = 180 runs $\approx$ **7.5 hours**.
- **Option B (Focused Matrix):** 4 strategies $\times$ 1 workload (W2) $\times$ 3 concurrencies (c=1, c=32, c=128) $\times$ 1 run = 12 runs $\approx$ **20 minutes**.

## 4. WP-GATE-2C: Idempotency & Transaction Boundaries

### 4.1 Schema & Proxy Corrections
1. Added Flyway migration `V5__idempotency_status_code.sql` adding column `response_status_code INTEGER DEFAULT 201`.
2. Mapped `responseStatusCode` in `IdempotencyRecord.java`.
3. Resolved Spring AOP proxy self-invocation by injecting `@Lazy private IdempotencyService self` and helper `getSelf()`, ensuring all internal transactional method calls traverse Spring's proxy.
4. Updated `IdempotencyService.execute()` to preserve and restore the original HTTP status code on idempotent replays (setting response header `Idempotent-Replayed: true` and status code).

### 4.2 Atomic Transaction Boundaries
1. Refactored `PaymentService`, `RefundService`, and `PayoutService` to invoke `idempotencyService.completeKey(scope, key, serialize(response), 201)` directly within the `@Transactional` business method (`Propagation.REQUIRED`).
2. If an exception occurs, the journal, ledger entries, outbox event, and idempotency completion record roll back together atomically.
3. Updated all posting engine strategies (`PostingEngine`, `S1LateLockStrategy`, `S2StripedStrategy`, `S4LedgerOnlyStrategy`) to look up journals by `(scope, idempotencyKey)` rather than unscoped `idempotencyKey`, preventing cross-tenant collisions.
4. Added `IdempotencyPostgresTransactionTest.java` verifying rollback atomicity, commit atomicity, and compound unique constraint backstops against live PostgreSQL 16.
